# note-cli で使っている技術の解説（非エンジニア向け）

このツールを作るのに使った技術を、プログラミング未経験の人にも分かるように説明します。
「なぜそれを使うのか」→「このツールのどこで使っているか」の順に書いています。

---

## 1. CLI（コマンドラインインターフェース）とは

ふだん使うアプリは、ボタンをクリックして操作します（GUI）。
CLI は、**黒い画面（ターミナル）に文字で命令を打って操作する**アプリです。

```sh
note-cli post 記事フォルダ/
```

この 1 行で「記事フォルダの中身を全部 note に上げて」という意味になります。

**CLI のいいところ**
- 同じ作業を何度でも正確にくり返せる（コピペで済む）
- 「100 ファイルまとめて」のような一括作業が得意
- 他の仕組み（定期実行など）と組み合わせやすい

---

## 2. Go（プログラミング言語）

このツールは **Go**（Google が作った言語）で書いています。先駆者が「Go が楽」と言っていた理由は主に 3 つです。

| 理由 | 説明 |
|---|---|
| **1 つのファイルで動く** | 完成品が `note-cli`（Windows なら `note-cli.exe`）という 1 個のファイルになります。相手の PC に Go や追加ソフトを入れてもらう必要がありません |
| **Windows / Mac / Linux どれでも作れる** | 同じプログラムから各 OS 用の完成品を作れます |
| **ネット通信や文字処理が標準で入っている** | note と通信する機能（`net/http`）や、データ形式 JSON を扱う機能が最初から付いています |

### Go の基本用語

- **パッケージ（package）**: 関連するプログラムをまとめた「フォルダ」のようなもの。このツールでは役割ごとに分けています
- **`go build`**: 書いたプログラムを、実行できる 1 個のファイルに変換（コンパイル）するコマンド
- **`go test`**: テスト（後述）を実行するコマンド
- **`go.mod`**: このプロジェクトが使っている外部ライブラリの一覧表

## 3. フォルダ構成（どこに何があるか）

```
note-cli/
├── main.go                 … 入口。プログラムはここから始まる
├── cmd/                    … 「login」「post」などのコマンドの定義
│   ├── root.go             … note-cli 全体の説明
│   ├── login.go            … login / logout / whoami
│   ├── new.go              … 記事のひな形を作る
│   ├── doctor.go           … API が想定どおりか確認する
│   └── post.go             … post（投稿）と check（チェック）、画像のアップロード
├── internal/article/       … 記事ファイルを読む・チェックする・HTML に変換する
├── internal/note/          … note.com との通信、ログイン情報の保存、仕様変更の検知
├── .goreleaser.yaml        … 完成品（配布用ファイル）の作り方
└── .github/workflows/      … GitHub Actions の自動実行の設定
```

**役割ごとに分ける**のがポイントです。たとえば note の API が変わったときは `internal/note/` だけ直せば済み、記事ファイルの書き方を変えたいときは `internal/article/` だけ見ればよくなります。

## 5. Markdown と HTML

- **Markdown**: 人が書きやすい「装飾付きテキスト」の書き方。`## 見出し` と書けば見出し、`**太字**` で太字になります
- **HTML**: Web ページの中身を表す書き方。`<h2>見出し</h2>` のようにタグで囲みます

note のエディタは内部で HTML を使っているので、このツールは Markdown → HTML に変換してから送ります（`internal/article/html.go`）。

変換時の工夫:
- note の見出しは「大見出し」「小見出し」の 2 種類だけなので、`#` / `##` → 大見出し、`###` 以下 → 小見出しにそろえる
- note は段落ごとに **ID（ランダムな番号）** を持っているので、同じように振る。有料記事の「ここから有料」の位置は、この ID で指定します
- `.txt` の改行がそのまま改行になるようにする（Markdown の普通のルールでは 1 回の改行は無視されるため）

## 6. フロントマター（記事ごとの設定）

ファイルの先頭に `---` で囲んで書く設定欄のことです。ブログツール（Hugo, Jekyll, Zenn など）でよく使われる書き方です。

```yaml
---
title: タイトル
status: published
price: 300
---
```

中身は **YAML** という形式で、「項目名: 値」と書くだけです。`[日記, Go]` は「リスト（複数の値）」を表します。

このツールでは、さらに**フォルダ共通の設定**（`note-defaults.yaml`）→ **記事ごとの設定** の順に重ねる仕組みにしています。CSS や多くのツールで使われる「全体の既定値を、個別の設定で上書きする」という考え方です。

## 7. API と「非公式 API」

### API とは
**プログラム同士がやり取りするための窓口**です。人は note の画面をクリックして投稿しますが、その裏ではブラウザが note のサーバーに「この記事を保存して」というメッセージ（HTTP リクエスト）を送っています。この窓口が API です。

### HTTP リクエストの基本
| 用語 | 意味 | このツールの例 |
|---|---|---|
| **URL（パス）** | どの窓口か | `/api/v1/text_notes` |
| **メソッド** | 何をしたいか。GET=取得、POST=作成、PUT=更新 | 下書き作成は POST、公開は PUT |
| **JSON** | データを送るときの書式 | `{"name": "タイトル", "price": 300}` |
| **ステータスコード** | 結果の番号。200 番台=成功、401/403=認証エラー、404=窓口がない、422=中身が不正 | エラー時にヒントを表示 |

### なぜ「非公式」？
note は外部向けの API を公開していません。そこで先駆者たちは、**ブラウザの開発者ツールで note の通信をのぞいて**、どの窓口に何を送っているかを調べました。このツールはその調査結果を使っています。

そのため note が中身を変えると動かなくなる可能性があり、それに備えて:
- `--dry-run` で送る中身を確認できる
- `extra:` で送る項目を自分で足したり上書きしたりできる

ようにしています。

### このツールが行う通信の流れ

```
1. GET  /api/v2/current_user                  … 自分は誰か確認（＋合言葉 XSRF トークンを受け取る）
2. POST /api/v1/text_notes                    … 空の下書きを作る（初回だけ）
3. POST /api/v3/images/upload/presigned_post  … 本文の画像ごとに「アップロード許可証」をもらい、
   POST （Amazon S3）                           … 許可証を付けて画像を保存先に直接送る（新しい画像だけ）
4. POST /api/v1/image_upload/note_eyecatch    … 見出し画像を設定（変わったときだけ）
5a. POST /api/v1/text_notes/draft_save        … 下書きにタイトルと本文を保存   （下書きの場合）
5b. PUT  /api/v1/text_notes/{記事ID}           … 全設定を付けて公開・更新       （公開の場合）
6. GET  /api/v3/notes/{記事キー}               … 公開できたか読み直して確認     （公開の場合）
```

先駆者の調査で「タグや価格は下書き保存では無視され、公開時（3b）にしか反映されない」と分かっているので、それに合わせた作りになっています。

## 8. ログインの仕組み（Cookie と XSRF トークン）

- **Cookie**: Web サイトがブラウザに預ける「会員証」のようなもの。note では `_note_session_v5` という Cookie が「ログイン済みの証拠」です。このツールはこれを保存しておき、毎回 note に見せます
- **XSRF トークン**: 「本当に note の画面からの操作か」を確かめる合言葉。悪意あるサイトがあなたになりすまして投稿するのを防ぐ仕組み（CSRF 対策）です。書き込みのたびにヘッダーに付けて送ります

### セキュリティ上の工夫
- ログイン情報のファイルは **自分だけが読み書きできる権限（0600）** で保存
- パスワード入力中は画面に文字を表示しない
- パスワード自体は保存しない（保存するのは Cookie だけ）

---

## 9. 安全に使うための工夫（設計の考え方）

| 工夫 | 理由 |
|---|---|
| 既定は**下書き** | 公開はやり直しがききにくいので、明示的に `status: published` と書いたときだけ公開 |
| 公開前に**確認**を出す | 間違って有料記事や未完成の記事を公開しないため |
| **全ファイルを先にチェック** | 10 件中 3 件目でエラー…のような中途半端な状態を避ける |
| `.note-cli.json` に**投稿済みを記録** | 同じファイルを 2 回 post しても、記事が 2 つにならず「更新」になる |
| 下書き作成直後に記録を保存 | 途中で通信エラーになっても、次回は同じ下書きを使う |

## 10. テスト

`go test ./...` で、プログラムが正しく動くかを自動で確認できます。

- `internal/article/article_test.go`: 記事ファイルの読み込み、有料部分の分割、価格チェックなど
- `internal/note/client_test.go`: **偽物の note サーバー**をその場で立てて、正しい窓口に正しい中身を送っているかを確認。「API が変わったら止まる」ことも、わざと変な応答を返して確認しています
- `cmd/post_test.go`: 同じファイルを 2 回投稿しても記事が増えず、変わっていない画像を再アップロードしないことを確認

本物の note に接続しないので、何度実行しても大丈夫です。
「偽物のサーバーで試す」のは、外部サービスと通信するプログラムをテストするときの定番の方法です（Go では `net/http/httptest` という標準機能で簡単にできます）。

## 11. 画像アップロードの仕組み

note に画像を送るときは、**2 段階**になっています。

```
あなたの PC ──①「cat.png を上げたい」──▶ note
           ◀──「この許可証で S3 に置いて」──
           ──② 画像 + 許可証 ──────────▶ Amazon S3（画像の保管庫）
```

- **Amazon S3**: Amazon が提供するファイル置き場。note は画像をここに保存しています
- **署名付き URL（presigned post）**: 「この場所に、この時間内なら 1 回だけ置いてよい」という一時的な許可証。note のサーバーを経由せず、大きな画像を直接保管庫に送れる仕組みで、多くの Web サービスが使っています
- **multipart/form-data**: 文字と画像ファイルを 1 回の通信でまとめて送るための形式。ブラウザでファイルを添付して送信するときと同じです

### 同じ画像を何度も上げない工夫（ハッシュ値）
画像の中身から **SHA-256** という計算で「指紋」（64 文字の英数字）を作り、`.note-cli.json` に「この指紋の画像はこの URL」と記録しています。

- 中身が同じなら指紋も同じ → 前回の URL を使い回す（ファイル名が違っても同じ）
- 中身が 1 ピクセルでも違えば指紋が変わる → 新しくアップロード

ファイルのダウンロードサイトにある「チェックサム」も同じ仕組みです（GoReleaser が作る `checksums.txt`）。

### AI で作った画像を使うには
このツールは「画像ファイルを note に上げる」担当です。画像生成は手元の AI で行い、できた画像を記事フォルダ（例: `images/`）に保存して `![説明](images/xxx.png)` と書けば使えます。
「作る」と「上げる」を別々の道具に分けておくと、使う AI を変えてもこのツールはそのまま使えます。

## 12. API が変わったとき（自動停止の仕組み）

非公式 API は、note の都合でいつでも変わります。変わったことに気づかず投稿を続けると「公開したつもりが下書きのまま」「有料のつもりが無料で公開」のような事故になりかねません。そこで **「想定と違ったら止まる」** 作りにしています（`internal/note/changed.go`）。

| 検知のしかた | 例 |
|---|---|
| ステータスコード | 404（窓口が無い）/ 405（その方法は使えない）/ 410（廃止） |
| 応答の形式 | JSON のはずが HTML（メンテナンス画面など）が返ってきた |
| 必要な項目の有無 | 記事 ID や画像の URL が応答に入っていない |
| **結果の読み直し** | 公開後に記事を取得し、公開状態と価格が送ったとおりか比べる |

最後の「読み直し」が特に大事です。API は「200 OK（成功）」と返しながら、送った項目を**黙って無視する**ことがあるからです（先駆者も、下書き保存でタグが無視される現象を報告しています）。

このように「入力や結果を確かめて、おかしければすぐ止まる」設計を **フェイルファスト（fail fast）** と言います。

### 止まったときの直し方
1. note の画面で、記事がどういう状態になっているか確認する
2. `note-cli doctor` で、どの窓口がおかしいか確認する
3. ブラウザの開発者ツール（F12 →「Network」）を開いて note の画面から同じ操作をし、今の窓口・項目名を調べる（次の章と同じ手順）
4. `internal/note/client.go` の該当部分を直す。項目名の違いだけなら、記事の `extra:` で一時的にしのげることもあります

### 定期チェック
`.github/workflows/api-check.yml` が毎週 `doctor` を自動実行します（後述の GitHub Actions）。投稿しない日でも、仕様変更に先に気づけます。

## 13. 予約投稿の調べ方

予約投稿の項目名はまだ分かっていません。次の手順で調べられます。

1. Chrome で note にログインし、新しい記事を書いて「公開に進む」画面まで行く
2. **F12** で開発者ツールを開き、**Network（ネットワーク）** タブを選ぶ
3. 上の検索欄に `text_notes` と入れて絞り込む。左上の 🚫 ボタンで一覧を空にしておくと見やすい
4. 予約日時を設定して「予約投稿」する
5. 一覧に出た通信（たぶん `PUT .../text_notes/数字`）をクリック →「**Payload（ペイロード）**」タブを見る
6. 日時が入っている項目を探す（例: `"publish_at": "2026-11-01T09:00:00+09:00"` のような形）。日時の書き方（タイムゾーンの付け方など）もメモする
7. 確認のため、その記事の予約は note の画面で取り消しておく

項目名が分かったら、CLI を改造しなくても次のように試せます:

```yaml
---
title: 予約投稿のテスト
status: published
extra:
  publish_at: "2026-11-01T09:00:00+09:00"   # ← 調べた項目名と書き方に合わせる
---
```

ただし今の CLI は「公開後に status が published になったか」を確認するので、予約だと status が別の値になり、**自動停止が働くはず**です（それ自体が「予約になった」証拠になります）。そのときのエラー表示に出る status の値もメモしておくと、正式対応するときに役立ちます。

> ⚠️ 調べるときは、**Cookie の値やトークンを他人に見せたり、スクリーンショットで公開したりしない**でください。

## 14. GoReleaser（完成品を作って配る）

Go で作ったプログラムは、OS（Windows / Mac / Linux）と CPU の種類（Intel 系 = amd64、Apple シリコン など = arm64）ごとに別の完成品が必要です。全部を手で作るのは大変なので、**GoReleaser** に任せます。

設定ファイル `.goreleaser.yaml` には次のことを書いています:
- 6 種類（3 OS × 2 CPU）の実行ファイルを作る
- Windows は zip、それ以外は tar.gz にまとめ、README とサンプルも同梱する
- `note-cli --version` で表示されるバージョン番号を埋め込む
- 作る前にテストを実行する（テストが落ちたら作らない）
- `checksums.txt`（ダウンロードしたファイルが壊れていないか確認する指紋）を作る

```sh
goreleaser release --snapshot --clean   # 手元で試しに作る → dist/ フォルダ
```

**バージョン番号**は `v1.2.3` の形（セマンティックバージョニング）が一般的です。
- 1 つ目（メジャー）: 使い方が変わる大きな変更
- 2 つ目（マイナー）: 機能追加
- 3 つ目（パッチ）: バグ修正

## 15. GitHub Actions（自動実行）

**GitHub Actions** は、GitHub が用意してくれる「自動で作業してくれるロボット」です。「コードが push されたら」「毎週月曜に」などのきっかけで、GitHub のサーバー上で決められた作業を実行します。料金は、公開リポジトリなら無料、非公開でも毎月の無料枠があります。

設定は `.github/workflows/` の YAML ファイルに書きます。

| ファイル | きっかけ（on） | 作業（jobs） |
|---|---|---|
| `ci.yml` | push / プルリクエスト | テストを実行。壊れた変更に ❌ が付く |
| `release.yml` | `v0.1.0` などのタグを push | GoReleaser で完成品を作り、Releases ページに公開 |
| `api-check.yml` | 毎週月曜 9:17（日本時間）/ 手動 | `doctor` で note の API を確認。失敗するとメールが届く |

用語:
- **CI（継続的インテグレーション）**: 変更のたびに自動でテストし、壊れていないか確かめ続けること
- **ワークフロー / ジョブ / ステップ**: 自動作業のまとまり / その中の仕事 / さらにその中の 1 手順
- **シークレット（Secrets）**: パスワードなどを、コードに書かずに GitHub に安全に預ける仕組み。ログには `***` と伏せ字で表示されます
- **cron**: 「毎週月曜 0 時 17 分」のような定期実行の書き方（`17 0 * * 1`。GitHub では世界標準時なので、日本時間では 9:17）

### 動かし方
1. このリポジトリを GitHub に push する（`ci.yml` が自動で動く。「Actions」タブで結果が見られる）
2. リリース: `git tag v0.1.0 && git push origin v0.1.0` →「Releases」に完成品が並ぶ
3. 週 1 チェックを使うなら: リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で、名前 `NOTE_SESSION`、値に `_note_session_v5` を登録

> ⚠️ `NOTE_SESSION` はあなたの note アカウントを操作できる鍵です。`doctor` は読み取りしかしませんが、鍵自体は強力なので、心配なら登録しなくても大丈夫です（その場合 api-check は何もせず終わります）。ログアウトすると鍵は無効になるので、そのときは登録し直してください。
> また、GitHub はリポジトリに 60 日間変更がないと定期実行を自動で止めます。
